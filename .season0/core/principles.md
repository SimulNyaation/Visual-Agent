# 설계 원칙

모든 도메인과 프로젝트에 공통 적용됩니다. 판단이 모호할 때 기준 문서로 사용합니다.

---

## P1. 3계층 신뢰 모델

```
  권고 (Advisory)       AGENTS.md, 스킬, 요청 명세         ← 해석에 의존, 무시될 수 있음
  검증 (Verification)   런타임 검증, 테스트, 상태 다이어그램
  강제 (Enforcement)    타입, 린트, 모듈 경계, API 설계     ← 예외 없이 적용
```

의존도가 높은 규칙일수록 하위 계층(강제)에 배치합니다. 권고 계층은 기계적으로 판정할 수 없는 판단 사항만 담도록 최소화합니다.

## P2. 교정 사항은 결정적 검사로 전환한다

동일한 교정이 2회 이상 발생하면 먼저 검토합니다. **"이 교정을 결정적 검사로 표현할 수 있는가?"**

- 가능 → 린트 / 타입 / 테스트 / 구조로 구현 (`/season0-enforce`)
- 불가능(판단 필요) → AGENTS.md에 한 줄 추가

검사의 오류 메시지에는 **위반 사유**와 **권장 대안**을 반드시 포함합니다. 차단만 하면 에이전트는 다른 우회 방법을 찾습니다.

## P3. 안티패턴은 전파된다

에이전트는 기존 코드를 참조해 패턴을 학습합니다. 안티패턴 하나가 이후 변경에서 복제되어 확산됩니다.

- 규칙을 추가할 때 **기존 위반 사례의 정리 계획을 함께** 수립한다
- 임시 우회 코드보다 **근본 원인 해결**을 기본값으로 한다
- 우회 코드를 정당화하는 주석은 작성하지 않는다. 이후 에이전트가 이를 허용 근거로 재사용한다

## P4. 요구사항 입력도 검증 대상이다

AI 산출물만 검증해서는 충분하지 않습니다. **요구사항이 모호하면 산출물 품질도 보장되지 않습니다.**

- 원문 요청은 보존하고, AI가 기술 명세로 변환한다
- 명세에서 요청자가 명시한 사항과 **AI 가정 사항을 분리 표기**한다
- 명세 이해도 검증은 **요청자 본인의 책임 영역**이다. AI는 이해도 검증을 수행하지 않는다
- Human 승인 전에는 구현하지 않는다

## P5. 완료는 증적으로 판정한다

"완료했습니다"는 완료의 근거가 아닙니다. 승인된 **인수 기준 각각**에 대해 객관적 증적이 필요합니다.

- 충족 / 미충족 / **미검증**을 구분해 보고한다
- 증적 없는 충족 판정은 없다
- 최종 판정은 Human이 한다

## P6. 적용 순서를 지킨다

```
Inner Loop 품질 확보 → 교정 사항의 규칙 강제화 → 검증 체계 구축 → Outer Loop 자동화
```

Inner Loop 품질이 확보되지 않은 상태의 자동화는 결함 생산 속도와 비용만 증가시킵니다.

## P7. 설계 근거는 ADR로 관리한다

설계 결정은 코드 주석이 아닌 `.season0/decisions/`의 ADR로 남깁니다. 결정 내용, 검토한 대안, 선택 근거를 기록해 동일한 논의의 반복을 방지합니다.
